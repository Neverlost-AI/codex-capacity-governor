## Proposed objective and dependencies

From an immutable T005 composed attempt, create an explicitly governed development-run record, preserve factual outcome/amendment evidence, and show bucket-specific forecast-versus-actual comparison when a separately reviewed actual is compatible. Reopen both a governed run and its original plan without treating either historical result as current authorization. Preserve all T002 `UNGUIDED` records and their exact recording vocabulary.

Dependencies: accepted T001/T002 recording and append-only persistence; accepted Gate A/Decision 0002 and Gate B/Decision 0003; founder-accepted and merged T005 at PR #11; founder-approved decisions below; reviewed additive schema/contract proposal; a clean accepted-main implementation baseline and a separate grant. The pure policy engine remains independent of outcomes. T007 is a later required validation stage, not this implementation's acceptance shortcut.

## Proposed user path and allowed surfaces

1. A paired local operator selects an existing saved T005 attempt. The UI displays its exact revision, receipt, forecast, policy result, configuration/method/profile versions and historical status. It must not imply that an input rejection, `NOT_COMPOSABLE`, or restrictive result authorized execution. Whether a governed record may be attached to each negative attempt family is a founder decision; a browser label alone must not establish guidance.
2. The operator explicitly identifies the run and its plan relationship. The server verifies the admitted local session, same project/repository/scope, persisted immutable attempt and receipt, exact bucket identities, and allowed result family. No browser-authored `trusted`, `guided`, actor, forecast, plan, or normalized-actual flag is authoritative. F8's local pairing/origin/CSRF boundary still applies; it is not general identity authentication or proof that the operator actually obeyed guidance.
3. The operator records the existing Decision 0001 factual outcome (`COMPLETED`, `PARTIAL`, `FAILED`), independent validation result, up to one raw manual consumption per existing category, optional remaining-capacity snapshot, unexpected failures, deferred work, and notes. Missing categories remain unknown, not zero. The optional new guidance/adherence evidence must have a separately approved vocabulary and must not be inferred from run outcome, validation, consumption, or a policy result.
4. A correction appends a complete reasoned observation referencing the current predecessor. Original and intervening observations, original T005 attempt, normalization review and comparison provenance remain recoverable. Recompute a derived comparison against the effective observation without rewriting the issued forecast or silently mutating a past comparison. A stale concurrent amendment fails.
5. Project/run history shows `UNGUIDED` and governed records distinctly, including missing outcomes, negative/incomplete outcomes, amended evidence and explicit comparison-unavailable reasons. It shows bucket identities and source units, never aggregates independent bucket capacities or offers an overall accuracy percentage.

Proposed allowed implementation surfaces after approval: `packages/contracts` additive governed-run, linkage, reviewed-normalization, comparison/adherence transport schemas; `packages/application` run/outcome/normalization/compare/history use cases and repository ports; `apps/web/src/server/db` additive persistence adapter/migration; `apps/web` paired local UI and accessible history; focused tests and implementation notes. Use `packages/forecast-engine` existing pure comparison semantics without changing formulas for an outcome-only T006. A later history loader/V2, if approved, requires its own pure-engine, contract, application and persistence boundary. The policy engine is read-only to this tranche.

## Evidence and compatibility boundaries requiring founder approval

- **Immutable linkage:** Choose the exact additive relationship for a governed run to one persisted T005 attempt/revision/receipt and the historical `Project`/`PreflightDraft`. T002's `guidanceKind` contract and `development_runs_unguided_only` DB check currently admit only `UNGUIDED`; no placeholder `GUIDED` value or backfill is valid. Preserve legacy rows and create a reviewed additive migration/compatibility reader. Do not relabel an old `UNGUIDED` run because a plan exists later. Define whether one attempt may have multiple runs, and which T005 result families may be linked, before migration.
- **Authority and provenance:** A server-generated link receipt should identify the admitted local session, actor reference, system record time, exact attempt/revision/receipt, plan/result family, bucket set and explicit user confirmation. The founder must approve whether this is adequate evidence of a *governed* run, given local F8 limits and deferred upstream authentication. It proves recorded confirmation, not real-world adherence or legal identity. Never accept a browser trust flag.
- **Actual compatibility:** Decision 0001's raw `amount`/`unit`/`source=manual` and optional remaining snapshot have no bucket identity or accepted conversion to forecast basis points. Propose a separate, explicit per-bucket, per-outcome-observation normalization assertion retaining source entry reference, original value/unit, provider/window/reset/profile IDs, exact normalized implementation amount, mapping/rule version, source evidence, reviewer/actor and record time. Its authority, supported units and whether human-reviewed direct bp/%/fraction entries may use Gate A's exact whitelist require founder approval. No provider-credit conversion, cross-bucket borrowing, or inferred allocation from one category entry. The raw observation remains intact even when normalized evidence is rejected or superseded.
- **Recording versus interpretation:** Keep Decision 0001 run/validation/consumption/deferred vocabulary unchanged. A new guidance/adherence field is distinct from those facts. Decide whether adherence is `FOLLOWED`, `PARTIALLY_FOLLOWED`, `NOT_FOLLOWED`, `UNKNOWN`, or a factual account instead; none is accepted yet. Do not infer compliance from forecast error or claim a Governor decision caused an outcome. Remaining-capacity snapshots are factual, not a derived reconciliation; any reconciliation rule is separate founder policy.
- **Comparison:** For a compatible `COMPLETED` run and bucket, report Decision 0003's `SignedError = Actual - issued Expected`, absolute error, range hit and `CalibrationRatio = Actual / issued Expected` using the immutable original forecast. Preserve exact and displayed values and explicit denominator identity. `PARTIAL`/`FAILED` normalized consumption may be shown only as a lower bound, never full-completion forecast error or calibration input. Missing outcome, missing category, zero expected, incompatible unit/profile/bucket, superseded or invalid normalization, and non-evaluable forecast return typed unavailable/non-comparable states; no fabricated zero. No overall accuracy percentage.
- **History query versus calibration loader:** This proposed T006 exposes factual and comparison history to users. It does **not** pass database candidates to `evaluateForecastV1`; T005 currently supplies `calibrationCandidates: []`. If the founder chooses the larger T006 option, separately specify the history loader's one-candidate-per-effective-run/bucket rule, 90-day evaluation-time recency, same project/repository, bucket class, method/config/profile compatibility, completed-only evidence, exclusion reasons, immutable replay and reset-cycle treatment. Historical reset-cycle comparability is still deferred, not solved by a guessed identity join.

## Migration, rollback, and acceptance proposal

The implementation proposal must show a forward migration from populated T001/T002/T005 records, exact constraints/indexes, no destructive rewrite or backfill, and stable reads of legacy `UNGUIDED` runs and saved attempts. Preserve source and amendment chains. App rollback should leave additive evidence tables intact; dropping them would destroy history and requires separate authority. Historical comparison should be reproducible from the issued attempt plus effective reviewed actual and versioned normalization, including amendment history; corrupt or unverifiable snapshots fail visibly, never repair themselves.

Required evidence before review: contract parsing and boundary tests (identity, missing/zero, incompatible units, result families); application success/validation/authorization/dependency-failure and stale-amendment tests; deterministic exact per-bucket comparison and `PARTIAL`/`FAILED` lower-bound tests; migration/DB integration and rollback-read compatibility tests; accessible UI/component tests for all meaningful states; at least one real paired-browser critical path from saved T005 attempt through governed outcome, amendment, comparison, reopen, plus denied/negative paths. Existing T001/T002/T005 regressions, typecheck, lint, full test, coverage, build, migration generation/check, changed-file canonical format and diff hygiene must pass or be reported precisely. A separately approved loader/V2 would additionally require sequential repeated-workload and mixed-cohort deterministic boundary tests from the concern analysis; it is not hidden inside outcome tests.

No automatic execution, AI decomposition, provider access, credential use, Claude Code, external hosting, tenant identity, pricing/credit conversion, retroactive Gate A change, opaque learning, or accuracy/savings claim is in this proposed slice. Do not weaken tests to satisfy a gate. The implementer must stop for any new evidence authority, normalization, run-linkage, method, budget or public-contract semantic choice. After founder approval only, create a focused `codex/` branch from the approved clean baseline and submit a PR with scope/exclusions, assumptions, decisions, tests/screenshots, migration/rollback and open questions.
