# T007 public challenge starters and acceptance tests — DRAFT freeze plan

**Preparation only; no measured build, external checkout or dependency install is recorded here.** The founder selected the three full public briefs, accepted medium/medium/large sizes, and accepted the URL Shortener restart-persistence adaptation. This document fixes the *source* revisions and predeclared checks. It does **not** claim that runnable derived starter commits, lockfile integrity, test code or a model/profile have been frozen; those identities must be produced and reviewed before an execution grant. The three challenges test the Governor workflow and collect initial factual calibration observations, not forecast accuracy or automatic learning.

## Common clean-start and freeze protocol

1. Use only the pinned upstream specification and the listed solution-free starter. Do not show completed examples, other-arm answers, previous attempt transcripts or final test implementation to the coding agent. Keep each starter's attribution/license terms. The three workspaces must be separate from the Capacity Governor source repository; the later execution grant must identify authorized locations.
2. In a **pre-measurement preparation** step, create one immutable derived starter commit per challenge containing only the upstream boilerplate, a reviewed lockfile if absent, local-only storage fixture/configuration where specified, and a minimal test runner needed to start the app. No solution logic. Record source SHA, derived SHA, file manifest and diff proving no completed solution. For repeated attempts, make a fresh checkout from that **same** derived SHA and a fresh conversation; no state/DB/transcript reuse.
3. Proposed common runtime to verify: Node `v24.19.0` and npm `11.17.0` (observed in the planning workspace on 2026-09-28). This is **not frozen** until clean `npm ci` and startup are verified for each pinned starter; if a legacy lockfile is incompatible, propose a reviewed lockfile-only derivation and record both hashes before execution. Do not silently upgrade dependencies or change challenge behavior during a measured attempt.
4. Acceptance assessor: a separate fixed test harness, with behavioral cases below and a recorded commit/hash, independent of either future single-agent or builder/reviewer arm. Recommend the repository-pinned Playwright `1.62.1` for browser cases and a locked HTTP test client for API cases; pin the exact harness/runtime and test order before attempts. A task's implementation may add its own tests, but the common final assessor remains unchanged. No live freeCodeCamp grading service, example implementation or outside network dependency is required at assessment time.
5. Freeze the hosted Governor deployment SHA/config, authenticated operator, displayed capacity plan and each required bucket/reset, model/version/reasoning/client settings, allowed tools and role sequence, local storage/clock/timezone fixtures, acceptance-case list, 180-minute/1,500-bp **proposed** stop rule, and private evidence handling. This is a per-attempt manifest, not a policy-engine input. A change before run start creates a new reviewed manifest; a change during a run is an interruption/deviation recorded in its worksheet.
